## [Unreleased]

### Added
- Installing without the plugin, completely (decision D36): `bdd install-skills claude` installs the skills for Claude Code without the plugin (`~/.claude/skills`, or `.claude/skills` with `--project`), `--uninstall` removes exactly what the command wrote for any target (files that carry the installation note and the marked `AGENTS.md` block; anything else is kept; emptied folders are removed), and `--user` and `--project` choose the scope. A deterministic test walks a whole feature in soft mode without a model: hooks absent, self-reported approvals, a seeded edit of a locked spec detected at the implement gate, the state and `bdd status` saying soft, and `enforcement = "hard"` refusing the same approvals. The platform probe also checks Codex when it is on the path (`--codex-only`, `--claude-only`).

- APIs and databases (decision D31): the standards file has an API and a data section; a new `data` profile adds the instruction `{operation} ran at most {count:int} queries` (core vocabulary version 2) so that an N+1 problem is a failing scenario, bound in the Python adapter through a `queries_executed` seam and a stdlib `QueryCounter` with SQLAlchemy and Django hooks; the qa-designer seeds at least three records for a scenario about a collection; the system-analyst copies the contract from the project's schema file and draws tables and relations in the design view; the auditor's checklist has a section D (contract, migrations, schema, query counts, bounded results); new practice cards `api-design`, `database-schema`, `database-migrations`, `database-performance` and `database-engines`; the adapter guides show opt-in tables for contract and migration checks. Query counts and plans show "no N+1 here" and "uses an index", not behaviour at production volume.
- Language standards and quality checks (decision D30): `[adapters.quality.NAME]` tables in `.bdd/config.toml` name the project's own formatter, linter, type checker and deprecation check; `bdd check FEAT-n` runs them without a shell (exit status is the verdict) and records `.bdd/.runs/FEAT-n/quality.json`, and the implement and verify gates need a current passing result when the tables exist (no change without them; adopted features are not held to it). `.bdd/standards.md` (from `templates/standards.md`, created by `bdd init` or `bdd init --standards`) states the language and toolchain version, style, quality rules and deprecation policy; only the person edits and approves it, the guard and the tripwire protect it, `bdd doctor` warns while it is missing or a draft, and the agents read it. Practice cards for Python, TypeScript, Expo, Next.js, Kotlin, Swift, Go and Rust; auditor checklist section Q (standards followed, quality result, no deprecated API, current documentation consulted, nothing suppressed). Programs started by `bdd run`, `bdd check` and `bdd mutate` are looked up in `PATH` only (never in the project or the working directory), so a planted `ruff.exe` cannot stand in for the tool; script shims such as `npm.cmd` start on Windows, and a batch file is refused when an argument holds characters that cmd.exe reads as syntax. The guard also recognises `cd .bdd && echo x > standards.md` (and `config.toml`).

- `bdd install-skills codex|agents-md` (decision D28): installs greenlight's instructions for Codex (skills under `.agents/skills` or `~/.agents/skills`, with this installation's paths) or as a marked block in `AGENTS.md`; `--dry-run`, never overwrites a differing file without `--force`, refuses links that leave the project. `bdd doctor` has an `enforcement` check that warns when enforcement is soft or no hook has run, and a self-reported approval says on stderr that no hook verified it.
- The `generic-junit` adapter: any test runner that writes a JUnit report (decision D26). The project supplies the run command and step code; the adapter defines the contract (one command per feature, one JUnit file, test names that contain the scenario name, `BDD_EXPECTED_MISSING` for unbuilt seams), ships a standard-library sample runner so `bdd init --smoke` works, `tests/run_junit.py` to merge several report files into one, classification and scan defaults, and six runner cards (JUnit with Gradle, JUnit with Maven, pytest, jest, go test, dotnet test).

- The optional mutation check (decision D29): an `[adapters.mutation]` table in `.bdd/config.toml` (command words without a shell, `{files}`, `{out}`, `threshold`, `timeout`, `extensions`) and `bdd mutate FEAT-n [--check]`, which runs the tool on the production files changed since the red was proven and records `.bdd/.runs/FEAT-n/mutation.json`. When the table exists the verify gate requires a current result at or above the threshold and auditor checklist item E5 becomes blocking; without it nothing changes. The report is written outside the project, the tool must exit 0, and a check that covered nothing although production files changed fails. The Python adapter guide documents the opt-in; no tool is added as a dependency.
- The `ts-playwright-bdd` adapter (decision D25) for web interfaces in a real browser: Playwright with playwright-bdd and TypeScript, the `base` and `ui` profiles bound to drivers (pages, components, clock, stubs, network block, per-actor browser contexts), pinned test tooling in its own `tests/package.json` and lockfile, a bound run script and JUnit reporter, failure classification for the red gate, a sample feature, a guide and a CI note. The six `ui` instruction cards (`C.UI.OPEN`, `C.UI.ACT`, `C.UI.SEE`, `C.UI.NOT_SEE`, `C.STATE.GLOBAL`, `C.STATE.VERIFY`) are written.
- One test now checks, for every adapter, that each instruction of its declared profiles is bound and nothing else, that its settings load and that the plumbing it names is shipped; the Python-only version of that test is replaced by it.
- The agents' guard treats a `node_modules` folder, at any depth, as the project's environment, matched as a whole path segment (with or without a trailing separator, also after `cd`): no agent may write into it. The tripwire also watches the installed node test tooling next to a bound `package.json`: npm's `.package-lock.json`, the entry points the run starts and the manifests of the test packages. Package tools fail closed for agents: npm, pnpm, yarn and bun (found by the last path segment of any word, also run through node) are allowed only with a script or read-only subcommand as the first argument (`npm run ...`, `npm test`, `npm ls`, `npm view`, `npm audit` with report flags only, `--version`) and no package-changing word after it; anything else, including any flag but `--silent`, `-s`, `--no-color` and `--no-progress` in front of the subcommand, and `npx`, `pnpx`, `bunx` and `corepack` are refused, under the quoting, decoding and variable readings the guard already applies.

## [0.1.0] - 2026-10-20

First release: the full flow from feature request to verified code with the `python-pytest-bdd` adapter. See the entries below.

### Added
- The `adopt` skill (decision D27): `/greenlight:adopt "<area>"` brings one bounded area of an existing code base under greenlight by describing what it already does. It runs the normal phases with the normal agents and human gates, with `phases/adopt.md` as the plan: every scenario is tagged `@existing`, the tests pass from the start, and no production code changes. New: `bdd state init --adopt` (a feature `kind`), `bdd adopt FEAT-n --check` (A1 every scenario is `@existing`, A2 the bind gate recorded the production source, A3 the source is unchanged), enforcement of those checks in the implement and verify gates of an adoption feature, and checklist item S8 for the auditor.

- User documentation: a rewritten README and `docs/` pages for the quickstart, concepts, the step vocabulary (generated from `vocabulary/core.json`), adapters, upgrading, the FAQ and troubleshooting.

- The design view (decision D24): the system-analyst now writes `design.md` (Mermaid: components and data flow, key interaction, data model) next to `system.md`, from `templates/design.md`; `bdd design FEAT-n` checks it (fences closed, known diagram type, balanced brackets, nothing active such as `click`, `href`, `%%{init`, and every `%% interface: NAME` comment names a row of the Interfaces table in `system.md`); the system-map gate refuses a view that fails the check; the step-engineer and the implementer read it, `guided` shows it to the person before binding, the report includes it, and checklist item S7 asks the auditor whether the code follows it.

- Evidence hardening, third round (decision D23): the test runner never receives `PYTHON*` (except `PYTHONUTF8` and `PYTHONIOENCODING`), `LD_*`, `DYLD_*`, `BASH_ENV`, `ENV` or `NODE_OPTIONS`, and the Python adapter starts Python with `-X utf8 -I` (isolated: no working directory on the import path); the guard, the lock and the run digest share one pattern matcher (`**` is refused), and a step, driver or plumbing file that matches but was never locked is a violation in `bdd lock --check` and the gates; the tripwire also watches installed packages' `entry_points.txt` and pytest's dependencies. Under `auto` and `autopilot` an existing test that encodes the replaced behaviour is updated through the change flow instead of being left as a must-fix.

- Decision D24 on a design view before coding: Mermaid in a `design.md` written in the system-map phase, checked by the CLI, read by the step-engineer and the implementer; two public diagram skills were reviewed and not imported (tool pre-authorisation and an upload to a third-party service).

- Evidence hardening, second round (decision D23): which tests run and with what is now taken only from bound or person-managed places. The Python adapter starts pytest with its own settings file (`tests/pytest.ini`, `-c`), a conftest cut-off (`--confcutdir tests`) and no `PYTEST_*` variables (`scrub_env` in `[adapters.run]`), and `support` may hold patterns such as `tests/*/conftest.py`, so a settings or conftest file elsewhere in the project cannot steer a run and a new nested conftest is covered by the same limits as the steps. The interpreter comes from `python = ` in `.bdd/config.toml` (`bdd init --python PATH`) or an in-project `.venv`/`venv`, no longer from `GREENLIGHT_PYTHON` or `VIRTUAL_ENV`. The tripwire also watches an in-project environment (interpreter, `pyvenv.cfg`, `.pth` files, `sitecustomize`, the pytest packages), and agents are refused shell commands that install packages or write `.venv`/`venv`. In the red record, a file entry now matches only that file, not every name that starts with it.

- Evidence hardening after a security review of the above: the adapter's plumbing files (`tests/conftest.py`, `tests/test_features.py`, `tests/__init__.py`, the `support` paths of `adapter.toml`) are bound like steps, so nothing that decides how scenarios run can change once the red is proven, and `bdd lock FEAT-n --scope bind --bound` locks exactly the configured step, driver and support files; each recorded run names the interpreter that produced it (path and hash) and a gate refuses a run made with another interpreter than the project resolves to now; the tripwire watches that interpreter when it lives in the project and the guard keeps every agent out of `.venv` and `venv`; the red run is read once and the same bytes are checked and kept.

- Fixes from the first end-to-end runs (a real feature through the agents with Sonnet 5.5 and Haiku 5.5; both reached the red gate, Sonnet went on to a green, locked, traced feature and an audit that found a real mismatch). **Tests run in the project's environment**: the run command placeholder `{project_python}` is `GREENLIGHT_PYTHON`, the active virtual environment, a `.venv` or `venv` in the project, or else the interpreter running bdd; the Python adapter uses it, so an agent no longer has a reason to install packages into the machine's Python, and the agents are told never to. **The red proof is kept**: passing the bind gate copies the run into `red.json` (hash recorded in `state.json`), `bdd classify --run red` reads it, and later runs such as the auditor's reruns cannot overwrite the evidence. **A sanctioned seam instead of editing a core driver**: `System.complete(operation, fields)` fills in a request field the scenario left out; the guide says the core drivers are not edited. **Playbooks and skill**: examples that describe behaviour the system already has are tagged `@existing` when written (after reading the code), rules and examples stay proportionate to the request, under `auto` and `autopilot` the orchestrator uses the change flow itself instead of stopping to ask when nobody can answer, must-fix audit findings are fixed and re-verified up to twice, and requirements are installed only by the person.

- Dogfooding: `specs/` holds greenlight's own behaviour as Gherkin (lint, locks, trace and the project schema version: 12 scenarios with trace tags), written in the step vocabulary and run through the `python-pytest-bdd` adapter, which `specs/run_specs.py` scaffolds into a temporary folder around one file of our own (`specs/operations.py`, mapping logical names such as `lint` and `violations found` to the real tool), so nothing of the adapter is copied into the repository. CI lints the specs with `bdd lint` and runs them. `evals/run_e2e.py` and the `shop-api` reference app run a whole feature through greenlight with real agents and collect metrics (`evals/results/` is ignored).

- The `feature` skill (the orchestrator) and the `status` skill, and `bdd state next-id`. The orchestrator settles the autonomy level, creates the feature, then loops over the phases: it starts each phase's agent with the playbook and the artifacts, runs the checks itself (an agent's claim is not evidence), records assumptions, costs, gates and locks from the agents' reports, relays their questions to the person one at a time, stops at the rules and examples gates with the exact line the person must type, refuses to let agents change locked files (it hands those to the `change` flow) and limits each phase to three attempts. A test keeps its table in step with the phases, the agents and the machine gates. The front-matter parser also refuses a value that starts with a quote but does not end with it, and the argument hints of the skills are quoted accordingly.

- Fixed the `spec-auditor` agent and six instruction cards whose front matter was not valid YAML (`: ` inside an unquoted value; Claude Code refused to load the agent). The front-matter parser now rejects such values (`: `, ` #`, a trailing colon, a leading YAML indicator) with a message to put them in double quotes, and a test parses every agent, skill and card with it.

- `bdd change FEAT-n --reopen PHASE --reason "..."` and the `change` skill: the one sanctioned way to change something already approved or locked. In one step it releases the locks that guard what is reopened (spec and bind for the specification, bind for the system map, vocabulary or binding), revokes the human approvals that no longer stand (the rules and the examples for `specify` and earlier, the examples for `test-design` and `examples`), forgets the gate results from that phase on and the recorded red, moves the feature back and records the change in `state.json`. A revoked approval has to be given again by the person; approving the new examples locks the new text. The auditor checklist gains L6: every unlock in the lock history must match a recorded change. The skill asks the person for a clear yes after showing the consequences, and never reopens the specification because an agent asked.

- `bdd init [--detect] [--adapter NAME] [--autonomy LEVEL] [--smoke]` and the rewritten `init` skill. `--detect` lists the adapters whose detection rule matches the repository (a file by name pattern that mentions a keyword); `init` creates `.bdd/` (`config.toml` with the chosen autonomy and the adapter's profiles, `glossary.md`, a `.gitignore` for machine-local data) and applies the adapter, never overwriting a file, and can add an adapter to an existing project; `--smoke` runs the adapter's sample feature and removes every trace of the run. The skill walks through doctor, detection, the adapter and autonomy choice (always the person's), requirements, the smoke run and what comes next. The adapter CI job now also runs the init tests.

- The six agents in `agents/` (product-analyst, qa-designer, system-analyst, step-engineer, implementer, spec-auditor) with explicit tool lists, a model, the playbook they run, what they must not do and what their last message must contain. Only the step-engineer and implementer can edit existing files, the auditor has no writing tool, and none of them records a gate, assumption, cost, lock or approval: they report, and the orchestrator records, so an agent cannot pass its own gate. The path limits stay in the guard, and a test checks that the agent files and the guard's per-agent matrix name the same six agents. `review/checklist.md` is the auditor's checklist (T, S, L, E, A items, each with a blocking flag and how to check it, including the AI-test smells), and the playbooks now say who records what.

- Phase playbooks in `phases/` (discover, specify, test-design, examples, system-map, refine, bind, tasks, implement, verify, and a quick path for one small rule), each with the agent that runs it, the cards it reads, and the same five parts: inputs, steps, output files, gate, pitfalls. They name the exact `bdd` commands of each gate, including the human approvals and their `auto` and soft-enforcement variants, the red gate with `--record-red`, and the change-request exit when a locked file would need to change. Tests keep them consistent with the tool: every phase has one, every `bdd` command they mention exists, every gate they record is a machine gate of that phase, and every card and template they name exists.

- Artifact templates in `templates/` (`brief`, `rules`, `test-design`, `system`, `tasks`, `report`, `glossary`, `change-requests`), each saying who writes it and how it is read, with the id formats `bdd trace` and `bdd scan` parse, and a filled-in example feature in `docs/examples/order-discounts/` (brief, rules, test design, system map, tasks and an approved-style feature file). Tests check that the templates keep their sections and id formats, and that the example is consistent: `bdd lint` is clean, `bdd trace` shows no gaps, and the system map declares its dependency.

- Twenty-two instruction cards (`cards/instructions/C.*.md`), one for every core instruction of the `base`, `api`, `cli` and `lib` profiles: the semantics, how to apply it, the patterns, good and bad Gherkin, how the `python-pytest-bdd` adapter implements it, and known pitfalls. Tests keep them honest: every instruction of those profiles has a card, no card exists for an instruction that does not, and each card lists exactly the patterns in `vocabulary/core.json`. The `ui` instruction cards come with the UI adapter.

- Seven practice cards (`cards/practices/`) for the product and QA ideas of decisions D21 and D22: request decoder, blocking questions, story splitting, pre-mortem, test data, mutation check and stability rerun, each with the phase it belongs to, a worked example and known pitfalls. `phase` in a card's front matter must be a real phase.

- Knowledge cards: `cards/<kind>/<id>.md` with flat front matter (`id` equal to the file name, `kind`, `apply_when`, and for techniques `output` and `cost`, optional `pairs_with`) and required sections, always including `## Known pitfalls`. `bdd cards build [--check]` validates every card (kind matches folder, ids unique, `pairs_with` names real cards, sections present and non-empty) and writes `cards/index.json`; `--check` fails when the index has drifted, and a unit test does the same on every CI run. `bdd cards list [--kind K]` prints the front matter only, so an agent can choose cards cheaply. The first six cards are the test-design techniques: boundary value, equivalence partitioning, decision table, state transition, pairwise and negative cases, written for greenlight's rules, examples and trace tags.

- CI installs the adapter contract's requirements with `uv` (`uv pip install --require-hashes --no-build`) from the pinned `requirements-dev.txt`.

- Decision D22 on QA capability: ideas from four public QA skill collections (three MIT, one noncommercial-only) are adapted in our own words into the auditor checklist, technique cards, mutation and stability checks and a test-data card; no text is imported.

- The `python-pytest-bdd` adapter (`adapters/python-pytest-bdd/`: `adapter.toml`, `guide.md`, `ci.md`, `templates/`) and `bdd adapter list|apply NAME`, which copies the templates into a project without overwriting anything and registers the adapter (run, classify and scan tables) in `.bdd/config.toml`. Every core instruction of the `base`, `api`, `cli` and `lib` profiles is bound to a driver in `tests/steps/core_steps.py` (a test checks that none is missing and none is extra): fake-free seams in `tests/drivers/system.py` that raise `ExpectedMissing` (`BDD_EXPECTED_MISSING`) until the project implements them, logical-name maps in `operations.py` (an unmapped name is `NotMapped`, a test defect), a per-scenario world with an isolated workspace, an injectable clock, stubs that fail on unstubbed calls, and a real-network block. pytest options `--bdd-shuffle-seed` and `--bdd-scenario` give `bdd run --shuffle` and `--isolated`. A sample feature passes on a fresh scaffold; a contract test (in CI on Linux and Windows, skipped where `pytest-bdd` is not installed) scaffolds a project, runs it green, shuffled and isolated, passes `bdd scan` and `bdd lint`, and checks that a missing seam and a 404 classify as expected failures and an unmapped name as a test defect.

- Decision D21 on product-management capability in the discover phase: adapt ideas from three public PM skill collections in our own words (no text imported; one is CC BY-NC-SA and cannot be used in an MIT project), as cards and a discover playbook section, not new skills.

- `bdd run FEAT-n [--adapter NAME] [--shuffle [--seed N]] [--isolated]` runs an adapter's tests for one feature with the command from `[adapters.run]` in `.bdd/config.toml` (`by_tag`, `report`, optional `shuffle` and `isolated` words, `timeout`; placeholders `{root}`, `{python}`, `{tag}`, `{marker}`, `{out}`, `{seed}`, `{scenario}` are filled in after the command is split into words, so no value can add words, and nothing goes through a shell) and records the outcome in `.bdd/.runs/FEAT-n/latest.json` together with a hash of the feature files and every step and driver file. `bdd classify FEAT-n [--expect red|green] [--json]` classifies the recorded JUnit results per scenario with the adapter's `[adapters.classify]` patterns: `test-defect` (checked first), `expected-fail`, or `unknown`, which blocks. A valid red needs every scenario to fail as expected (a pass is allowed only for `@existing`); a green needs every scenario to pass. When an adapter has a run command, the `bind` gate needs a valid red and the `verify` gate a green from a run recorded against the files as they are now. The recorded runs are CLI-managed data that the guard keeps the agent out of, and test reports with a DOCTYPE or entity declaration are refused.

- Schema versioning of `.bdd/`: `version` in `.bdd/config.toml` (absent means 1). Every command except `doctor`, `migrate` and the hooks refuses a project that is newer than this greenlight with a message to upgrade it, and one that is older until `bdd migrate` has run; the guard stays closed on a newer project. `bdd migrate [--dry-run]` copies `.bdd/` to `.bdd-backup-v<N>` (and refuses to overwrite an existing backup), runs the registered step from each version to the next, and bumps `version` after each, so a failed step leaves the project at the last good version. There is no migration yet because schema 1 is the first; the mechanism is tested with a stand-in step.

- `bdd scan FEAT-n [--json]`: deterministic checks on the step definitions and drivers of an adapter, driven by its `[adapters.scan]` table in `.bdd/config.toml` (`step_start` with a `kind` group, `assert_patterns`, `sleep_patterns`, `stub_patterns`; invalid regular expressions are config errors). Reports `S2` a `then` step that never asserts, `E3` a fixed wait, `S4` a stub of something `system.md` does not list under its Dependencies heading (or no list to check against). Comment lines are ignored; exit 1 on findings, 2 on usage or config problems. The shuffled and one-scenario-per-process runs belong to `bdd run` and come with the adapters.

- `bdd status [--json]` lists every feature with its phase, autonomy, approvals, enforcement level and what it is waiting for (including the exact command the person has to type), plus open integrity violations. `bdd status --brief` is one line for the session start (a `SessionStart` hook prints it; silent outside projects or when nothing is in progress, and it never fails). `bdd trace FEAT-n [--json]` builds the rule, example, scenario and task matrix from `rules.md`, `test-design.md`, the tagged feature files and `tasks.md`, and reports gaps `T000`-`T007` (rule without example, example without scenario, unknown ids, scenario not owned by a task, untagged or unreadable scenarios); it only compares artifacts that exist, and exits 1 when there are gaps.

- `bdd doctor` inside a project checks the settings files (project, local, user and managed, read-only) for the recommended native deny rules and prints the exact JSON to add for the ones that are missing: no writes to `state.json`, `lock.json` or `.claude/settings*.json`, and no `claude plugin disable|uninstall` or `claude mcp add`. Claude Code applies these before any hook, so they hold against shell spellings the guard cannot read. Rule syntax was tried live. The `init` skill tells the model to relay the snippet rather than write it.

- Tripwire: the baseline and its backup are validated; a malformed or corrupt backup is reported as a violation (and replaced by the next prompt) instead of crashing the check, and malformed integrity data exits 2 to the model.

- Tripwire: a second copy of the integrity baseline is kept outside the project; while the project's copy is missing the tripwire still compares with the backup and checks the locked files, and restoring the baseline reports the differences found.

- Tripwire hardening (security review): a missing integrity baseline is now a violation instead of a fresh start, the baseline is only created or moved by the prompt hook, what that hook accepts is announced and kept in the baseline history, and unreadable integrity data is reported to the model (exit 2) and refuses the gates; the prompt hook itself never blocks a prompt.

- The integrity tripwire (`PostToolUse` runs `bdd tripwire`): after every file, shell and MCP tool call it compares the files that make greenlight enforce anything (Claude Code settings and hooks, the plugin's own files, `.bdd/config.toml`) with a baseline of their hashes and the locked specs and steps with their locks, whatever command produced the change. A difference is reported to the model at once (exit 2), kept in `.bdd/.integrity/violations.json`, and the `implement` and `verify` gates refuse while one is open; it closes when the file is back as it was. The baseline is taken on first use and moves only when the person submits a prompt and nothing is open (`bdd tripwire --accept`, run by the prompt hook). A test now checks that every command named in `hooks.json` exists, because an unknown command exits 2 and would block every prompt.

- Approval verification now reads what the person typed from the transcript and requires it to be exactly the recorded approval (feature, gate, approve or reject), and a prompt can approve only once. Before, an approval recorded with the prompt id of any prompt the person had typed (for example by calling the hook command from a shell with forged input) was accepted as human. Found by security review.

- The approval hook (`UserPromptSubmit` runs `bdd approve --from-hook`) and the `/greenlight:approve` skill. A prompt that is exactly `/greenlight:approve FEAT-n rules|examples` (optionally followed by `reject <reason>`) is recorded as a pending approval with the prompt id and transcript path; anything else, and any prompt outside a project, is ignored. It always lets the prompt through and prints one line that the skill relays. The skill cannot be invoked by the model. Origin checks now ignore the tool results that share a prompt's id. `evals/platform-probe/approve_e2e.py` checks the path live inside Claude Code.

- Human approvals: `bdd approve FEAT-n rules|examples --self-reported|--auto [--reject --reason ...]` and `--verify`. An approval records who gave it (`hook`, `self-reported`, `auto`), a hash of what was approved and the enforcement context. Approvals typed by the person are recorded as `pending` and checked against the session transcript (`origin.kind`, `turnOrigin`, `promptSource`, `promptId`); system-injected and, unless `[approvals] allow_headless = true`, headless prompts are not accepted. `enforcement = auto|hard|soft` in `.bdd/config.toml`: `hard` refuses self-reported approvals, `auto` refuses them once hooks have run in the project or while building the feature (the guard leaves per-session markers and a permanent one), `soft` accepts them. Approving examples locks the spec; rejecting unlocks it. Machine gates now refuse to pass unless the human gates they depend on are validly approved and unchanged.

- Repository skeleton, decisions record and verified platform notes.
- `bdd` CLI package skeleton (`tools/bdd`) with `--version`, and CI running the stdlib unit tests on Linux, Windows and macOS with Python 3.11 and 3.14.
- `tools/bdd/bdd` interpreter wrapper: tries `python3`, `python`, `py -3` by executing each (skips the Microsoft Store stub), caches the result in `${CLAUDE_PLUGIN_DATA}`, runs `python -I`; actionable message and exit 127 when no Python 3.11+. The cache lives in a private directory (never shared `/tmp`), is created with `umask 077`, and is trusted only if owned by the current user.
- `bdd doctor` (python, sh, git, hook-latency checks with fixes; `--json`).
- Plugin manifest and single-plugin marketplace (`/plugin marketplace add iadr-dev/greenlight`, `/plugin install greenlight@greenlight`), and an `init` skill that runs `bdd doctor`. Unit tests check the manifests, skill front matter and version agreement; `claude plugin validate` is part of the release checklist.

- Gherkin parser (`bddlib/gherkin.py`): Feature, Rule, Background, Scenario, Scenario Outline, Examples, steps, data tables, doc strings, tags and comments, with localized keywords for 80 languages (`# language: zh-TW`), line-numbered errors, and tag inheritance helpers. The keyword table is a trimmed copy of Cucumber's `gherkin-languages.json` (MIT).

- Core step vocabulary (`vocabulary/core.json`): 28 instructions in five profiles (`base`, `api`, `ui`, `cli`, `lib`) with English patterns and Traditional Chinese alternates, and `bddlib/vocabulary.py` to compile typed patterns (`{amount:int}`, `{state:enum(on,off)}`, `{duration}`), load a project's `vocabulary.toml` of domain steps that compose core instructions, and resolve step text to the instruction(s) it matches. Ambiguity is reported, never hidden.

- `bdd lint [paths]`: checks `.feature` files against the step vocabulary and reports `L001` parse errors, `L002` unresolved steps (with the closest pattern as a hint), `L003` ambiguous steps, `L007` instructions from a disabled profile, `L008` wrong table/doc-string shape, `L009` Scenario Outline parameter mismatches and `L011` `# proposed-step` warnings. Reads `.bdd/config.toml` and `.bdd/vocabulary.toml` when present; `--json` for tools; exit code 1 on errors, 2 on usage problems. It also enforces the rest of the vocabulary rules: `L004` implementation details in steps (URLs, HTTP verbs and status codes, SQL, selectors, code calls, class names; quoted values are data), `L005`/`L006` trace tags (`@FEAT-n`, `@R-n.m`, `@EX-n.m.k` present, well-formed, consistent and unique; `--no-trace-tags` for unmanaged files), and, for the project's own `vocabulary.toml`, `L010` near-duplicate patterns (similarity threshold from `.bdd/config.toml`, cleared by a `justification`) and `L012` domain steps that do not compose core instructions properly (must list them, in enabled profiles, and a `when`/`then` step must compose a `when`/`then` instruction). Because AI agents call it, it only reads `.feature` files and a `--vocabulary` `.toml` inside the project, so parse errors cannot be used to read other files.

- Hash locks: `bdd lock FEAT-n --scope spec|bind` records a SHA-256 for the approved `.feature` files (found by their `@FEAT-n` tag) or the step definitions and drivers proven red; `bdd lock FEAT-n --check [--require] [--json]` detects files that were changed, deleted, or (for specs) added after locking; `bdd unlock FEAT-n --scope S --reason "..."` releases a scope and keeps the reason in the lock history. Hashes ignore CRLF/LF differences so a Windows checkout is not mistaken for tampering. Only files inside the project can be locked. Data files are written atomically and carry a schema version; files from a newer greenlight are refused.

- Feature state in `.bdd/features/FEAT-n-slug/state.json`: `bdd state init|show`, `bdd gate FEAT-n <gate> --result pass|fail` for the machine gates, `bdd assume` (autonomous-run assumptions `A-n.k` with rationale and rejected alternatives), `bdd cost` (tokens and time per phase) and `bdd mode --switch LEVEL --reason "..."` (autonomy switches keep the user's words). Human gates (`rules`, `examples`) are refused here: only the person can approve them. Two gates are enforced by the tool: `implement` cannot be recorded as passed unless the spec and bind locks are intact (a weakened step or a spec added after locking is refused), and `verify` additionally needs `implement` to have passed. `bdd gate FEAT-n bind --record-red` records the git commit, whether production source had uncommitted changes, and a digest of the production source, so the red-before-code order can be proven later. State updates are serialised by a cross-process file lock (stale locks from crashed processes are broken) and writes retry briefly on Windows sharing violations.

- The guard hook (`hooks/hooks.json` + `bdd guard`), which runs before file edits, shell commands and the tools that can schedule or send prompts. Inside a project it blocks: edits to locked specs and bound steps (with the lock's feature and scope and how to change it properly); edits to CLI-managed data (`state.json`, `lock.json`, enforcement markers); writes outside what each greenlight agent may touch (product-analyst, system-analyst: `.bdd/` only; qa-designer: plus feature files; step-engineer: plus steps and drivers; implementer: production code but never tests; spec-auditor: nothing); shell commands that name a locked or managed file and look like a write (`sed -i`, redirections, `tee`, `cp`, `mv`, `rm`, `git checkout --`, Python/PowerShell one-liners); and any tool call that schedules, sends or invokes `/greenlight:approve` or `/greenlight:reject`, so the AI cannot approve its own work. Paths are compared in every spelling (relative, `..`, backslashes, symlinks, case on Windows/macOS). It does nothing outside a project, fails closed when lock data is unreadable and open (with a warning) on its own errors. `evals/platform-probe/guard_e2e.py` checks it live inside Claude Code.

- Fifth guard hardening round: shell commands are read after brace expansion (`.{claude,x}`), bash `$'...'` decoding, and environment-variable and `~` substitution (including `CLAUDE_CONFIG_DIR`), for both the enforcement files and the locked files, within a fixed bound; and the protected `.claude` children (settings, hooks, session transcripts) are one shared list used by both the text and the glob checks.
- Fourth guard hardening round: a second `claude` call placed after a read-only one (for example `claude --help $(claude plugin disable ...)`) was never examined because the first match swallowed the words after it; backslash-escaped spellings of protected paths and globs that can expand to `.claude` or its settings (`.cl*`, `.*`, `.claude/sett*.json`, decided by matching the glob against the real names) are now recognised; and the session transcripts that approvals are verified against can no longer be written by the agent.
- Third guard hardening round: `claude` commands in a project are limited to read-only forms (`plugin list`, `mcp list`, `--version`, ...) because `claude plugin disable` would switch greenlight off; the settings check looks at both the path as written and the resolved path (a `.claude` that is a symlink elsewhere); and shell commands that move, delete or replace the `.claude` directory, or spell its files with quote tricks, are refused.
- Second guard hardening round: every write to `.claude/settings*.json` is refused (content inspection could be dodged with JSON escapes), symlinked directories no longer hide the settings folder, and starting a nested `claude` session from a shell command is refused (management commands such as `claude plugin list` still work).
- Guard hardening after security review: inside a project the guard now fails closed on any failure (a broken `.bdd/config.toml` used to disable it); shell commands are checked for approval commands too (blocks a nested `claude -p "/greenlight:approve ..."`); and the plugin's own files, Claude Code hook settings and `.bdd/config.toml` are protected from edits made by the agent.

### Added (tooling)
- `evals/platform-probe/probe.py`: re-verifies the Claude Code behaviours the design depends on (hook shell, agent naming, approval-hook behaviour, transcript origin markers, `/loop` scheduling) against the installed CLI.

### Fixed
- CLI output is UTF-8 with LF endings on every terminal and code page (PowerShell, cmd, Git Bash); the wrapper runs Python with `-X utf8`.
- Wrapper failed with `MSYS_NO_PATHCONV=1` on Windows (native `python.exe` received an unconverted `/c/...` path); it now uses `pwd -W`. `bdd doctor` also says why it could not measure hook latency.
