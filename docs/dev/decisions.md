# Decisions

Record of design decisions. Add a row (or a section below) for every new one, with the reason.

| # | Decision | Status / rationale |
|---|---|---|
| D1 | File formats | **Decided:** TOML for human-edited files (`config.toml`, `vocabulary.toml`, `adapter.toml`) via stdlib `tomllib`; JSON for tool-owned files (`core.json`, `state.json`, `lock.json`, card index); flat YAML-style frontmatter only where Claude Code/Codex require it. Requires **Python 3.11+**, which is fine because 3.10 reached end-of-life in Oct 2026 |
| D2 | Python vs Node for the CLI | Python stdlib behind the `tools/bdd/bdd` wrapper; revisit if Windows hook latency or interpreter discovery is poor |
| D3 | Where `.feature` files live | **Decided:** adapter default paths, overridable per adapter in `config.toml` |
| D4 | Gherkin language default | **Decided:** follow the user's language (`language = "auto"`); IDs, tags and file names stay ASCII |
| D5 | Plugin name | **Decided:** `greenlight` for plugin, marketplace and GitHub repo (`iadr-dev/greenlight`). Commands `/greenlight:<skill>`, agents `greenlight:<agent>`, soft-mode stubs `greenlight-<skill>`. Chosen over bdd-forge/bdd-x-ai because "AI × BDD" names are common and "greenlight" describes the approval gate and red → green |
| D6 | License | **Decided:** MIT |
| D7 | Human approval mechanism | **Decided:** `UserPromptSubmit` hook with whole-prompt strict match + `disable-model-invocation: true` + guard denying scheduled approve text + transcript origin check (tests showed system-injected prompts also fire the hook — platform-notes P6, P14) |
| D8 | Orchestrator placement | **Decided:** `feature` skill in the main session, because subagents can't ask the user (P2) |
| D9 | Wrapper location | **Decided:** `tools/bdd/bdd`, not top-level `bin/`, so claude.ai/Cowork can still install the plugin (P11) |
| D10 | Skill count | **Decided:** 6 user-typed skills; phases are playbooks in `phases/` |
| D11 | Windows shells | **Decided:** hooks are POSIX `sh` commands, so hard enforcement on Windows requires Git for Windows (Claude Code then runs hooks in Git Bash whichever terminal launched it, platform-notes P13). Without Git, Claude Code uses PowerShell for hooks and the `sh` wrapper cannot run: greenlight works in soft mode and `bdd doctor` says how to get hard mode. Linux and macOS use their native `sh`. All CLI output is UTF-8 with LF endings regardless of terminal (P17) |
| D12 | Guard failure modes | **Decided:** inside a greenlight project the guard *fails closed*: if it cannot reach a verdict (unreadable or newer-schema lock data, a broken `.bdd/config.toml`, an internal error) the call is blocked and the message says how to recover. A guard that can be switched off by corrupting a file is not a guard (found by security review: a broken config used to be treated as unreadable input and allowed everything). It fails open only where it cannot tell whether it is in a project at all (hook input that is not valid JSON) and does nothing outside a project |
| D13 | Shell-command protection | **Decided:** best effort, matched on file names anywhere in the command text (any quoting or slash style, including paths built inside a Python one-liner), only when the command also looks like a write. It cannot foresee everything a shell can do (`git checkout main` may revert a file), so the hash check at the implement and verify gates is the guarantee and the hook is the first line of defence |
| D14 | Protecting what enforces greenlight | **Decided:** the guard refuses edits to the plugin's own files (`CLAUDE_PLUGIN_ROOT`), `.claude/hooks/`, **every** `.claude/settings*.json` (with symlinks resolved), and treats `.bdd/config.toml` as CLI-managed. Settings are refused whatever the change says: inspecting content for hook settings was bypassable with JSON escapes (`"hooks"`) and the person can still edit them or use Claude Code's `/permissions` and `/hooks` screens. It also refuses any tool call or shell command containing an approval command **and** any command that starts a nested `claude` session (only the read-only forms `claude plugin list|details|validate`, `mcp list|get`, `config list|get`, `doctor`, `--version` and `--help` pass: `claude plugin disable` would switch greenlight off), because a prompt typed into a nested session looks typed to the approval hook. A text denylist can never be complete (an approval can be assembled from pieces), so it is friction, not the safeguard: the authoritative control is that an approval is verified against the session transcript as human-typed, and a headless-origin approval is not accepted unless `[approvals] allow_headless = true`; it also protects the session transcripts that approvals are verified against (`CLAUDE_CONFIG_DIR/projects`), so the evidence cannot be rewritten |
| D15 | Limits of shell-command protection | **Decided, and stated plainly:** matching shell text cannot be complete. Globs (`.cl*/settings.json`), command substitution and encoded payloads can name a file without spelling it. The guard closes the cheap routes (quote splitting, operations on the bare `.claude` directory, symlinks, both literal and resolved paths) and is documented as friction. The guarantees that do not depend on parsing a shell are: the hash check at the implement and verify gates, approvals verified against the transcript, and `enforcement = "hard"` in `.bdd/config.toml`, which refuses self-reported approvals outright so that switching hooks off cannot be followed by approving one's own work. **Correction:** an earlier version of this row said Claude Code snapshots hook configuration at session start. It does not: settings files are watched and reloaded while a session runs (platform-notes P20), so a settings edit made by the agent would take effect at once. That is why the guard refuses every such edit, and why D16 matters |
| D16 | Native permission deny rules | **Decided:** the strongest boundary available is not ours. Claude Code evaluates `permissions.deny` rules before any hook, hooks cannot override them, and managed-settings deny rules outrank project and user settings (platform-notes P21). A plugin cannot ship such rules (not documented as possible) and the guard stops the agent from writing them, so the **person** adds them. `bdd doctor` and `/greenlight:init` will check the settings files (read-only) for the recommended set and say what to add: `Edit` and `Write` on `.claude/settings*.json`, `**/state.json` and `**/lock.json` under `.bdd`; `Bash(claude plugin disable:*)`, `Bash(claude plugin uninstall:*)`, `Bash(claude mcp add:*)`. Teams that need a guarantee deploy the same rules through managed settings |
| D17 | Detect by effect, not by spelling | **Decided (follow-up):** five rounds of review have each found another way to *spell* a path in a shell command (quoting, escapes, globs, braces, `$'...'`, variables, chained calls). The guard now covers those, but a text check will always lag the shell. The durable answer is to look at what changed: a PostToolUse check after each file or shell tool call that compares hashes of the locked files, the CLI-managed data, the plugin's own files and the Claude Code settings against what they should be, reports any difference to the model at once, and records it as a violation that the implement and verify gates refuse to pass over. That catches every spelling because it never reads the command. Together with native permission deny rules (D16) and hard enforcement (D15) the text matching becomes an early, friendly warning rather than the safeguard |
| D18 | Approval provenance and self-reporting | **Decided:** a hook-grade approval is stored `pending` because the person's prompt is not yet in the transcript when the hook runs; the gates verify it later from Claude Code's own origin fields and refuse anything not human (headless only with `[approvals] allow_headless`). Self-reported approvals exist for projects without hooks and are refused when `enforcement = "hard"`, or under `auto` once hooks have run in the project (a permanent marker the guard writes) or while building the feature (a one-way flag in the CLI-managed state), so deleting markers or unsetting the session id cannot reopen them; only the person editing `.bdd/config.toml` to `soft` can. Automatic approvals need autonomy `auto` or `autopilot` |
| D19 | Tripwire baseline and acceptance | **Decided (implements D17):** the baseline of enforcement files is taken on first use and refreshed only by the `UserPromptSubmit` hook while no violation is open. The agent acts during turns and the tripwire has already reported its changes by the time the next prompt arrives; the person edits between prompts. The baseline is only ever created or moved at a prompt: a baseline that is missing when a tool call finishes is itself a violation (deleting it is not a way to start over), and what a prompt accepts is listed to the model and kept in the baseline's history. A second copy of the baseline is kept under the user's Claude config directory (`greenlight/<project hash>/`), so with the project's copy deleted the tripwire still compares against it, still checks the locked files, and the prompt that restores the baseline reports every difference from the backup. Unreadable integrity data is reported to the model and refuses the gates. A change made mid-turn stays a violation until it is undone, so an intentional edit of settings should be made between prompts. Known limit: a prompt injected by the system also fires the hook, so a change made by a tool the `PostToolUse` matcher does not cover (it covers the guard's tools and every `mcp__` tool) would be accepted at the next prompt. User-level settings are watched but only read, never written, by greenlight |
| D20 | Recorded runs back the red and green gates | **Decided:** `bdd run` is the only writer of `.bdd/.runs/<FEAT>/latest.json` (CLI-managed, guarded), which holds the JUnit cases, the command words, the shuffle seed and a hash of the feature, step and driver files. `bdd classify` and the `bind` (valid red) and `verify` (green) gates read only that record, and refuse it when the hash no longer matches, so a test edited after it was run must be run again. The gates are enforced only when the adapter configures a run command; `.bdd/config.toml` is guard-protected and watched by the tripwire, so the requirement cannot be dropped by the agent. Commands are split into words before placeholders are filled and never run through a shell. A failure no pattern recognises is `unknown` and blocks, because guessing would let a broken test pass the red gate |
| D21 | Product-management capability | **Decided:** defining a feature needs product thinking, so the discover phase gets a PM toolkit, but as **our own words**, not imported text, and not as new skills (there stay six). Three public collections were reviewed (`phuryn/pm-skills` and `aroyburman-codes/pm-skills`, both MIT; `deanpeters/Product-Manager-Skills`, CC BY-NC-SA 4.0, which cannot be copied into an MIT project and whose non-commercial and share-alike terms would bind every user of greenlight). All three are generic chat prompts: long, interactive, no files, no gates, web-search steps, document templates that invite design before the rules are approved, and a large share about strategy, pricing and marketing. What is worth taking are ideas, which carry no copyright: **(1)** a request decoder (the literal ask versus the underlying job to be done, must-haves versus nice-to-haves, gaps and ambiguities, infer but never invent); **(2)** a blocking-question gate (at most three questions, one at a time, skipping what is already answered; anything else becomes a recorded assumption `A-n.k`, which `bdd assume` already keeps); **(3)** problem statement with goals and non-goals; **(4)** personas and job stories; **(5)** assumption mapping with risk ranking to choose the questions; **(6)** story splitting into thin slices; **(7)** problem-first prioritisation, only when several candidate features exist; **(8)** a pre-mortem over the draft rules (launch-blocking, tracked, or noise) before the person is asked to approve them; **(9)** INVEST hygiene that ends in Gherkin rules and examples with trace tags, never prose acceptance criteria. They become cards (kind technique, with pitfalls) and sections of the discover playbook when those exist, owned by the product-analyst agent, whose output is `brief.md` and `rules.md` and whose only questions are the gated ones. Left out on purpose: web research, long PRD templates, architecture or launch sections, pre-authorised tools, promotional links. No third-party text is included, so no notice file is needed; the docs credit the collections as inspiration |
| D22 | QA capability from public QA skill collections | **Decided:** four collections were reviewed against what greenlight's QA side needs (`petrkindlmann/qa-skills`, `PramodDutta/qaskills`, `saleem-daqa/qa-test-case-generation`, all MIT; `naodeng/awesome-qa-skills`, PolyForm Noncommercial 1.0.0, which cannot be used in an MIT project). None is a gated pipeline or BDD-shaped: they are long, tool-specific, partly auto-generated prompts (hundreds of skills, mostly Playwright, Cypress, performance, SEO and marketing material, plus a telemetry-sending installer in one), and none has the rule-to-example structure, trace tags or locks. Nothing is copied, no notice file is needed, and the docs credit them as inspiration. What is worth taking, rewritten as cards and checklist rows: **(1)** the auditor's verdict per test as strong, weak or fake, judged by *the smallest realistic bug that should make it fail*, with a blocker, major, minor ladder, a traceability gate and a ban on vague expected results ("works correctly"); **(2)** more AI-test smells for the checklist: self-comparison, status-code-only checks, swallowed failures, coverage padding, a closed loop where tests are written from the implementation, fabricated imports, generic test data, while a mock at a declared external boundary stays acceptable and mocking the system under test does not; **(3)** mutation testing as an optional verify-phase check scoped to the changed production files, with survivors fed back as missing examples, a threshold that only ratchets up, equivalent mutants handled by hand, no chase of 100%, and a low kill rate on AI-written tests read as 'the tests are not independent of the implementation'; **(4)** a stability rerun on the same commit that classifies a failure as product, test, environment or data and only diagnoses and proposes, never auto-fixes or quarantines; **(5)** technique cards that say 'name the technique in the example', 'one invalid input at a time', 'an unanswered decision-table cell is a requirement bug', boundary probes per field type (below min through above max, whitespace only, bytes versus code points, leap day, start after end, double submit) and a duplicate rule ('can this case fail independently?'); **(6)** a test-data card: each scenario owns its data, factories over shared fixtures, deterministic seeds, mask personal data. Equivalence partitioning, decision tables, state transitions and pairwise are written from standard testing literature, because the collections add little there. Where it lands: `review/checklist.md`, the cards, and the verify playbook; the deterministic parts (self-comparison, status-only assertions) are candidate rules for `bdd scan` |
| D23 | What the test evidence depends on | **Decided (after the first end-to-end runs and three security reviews):** a gate accepts a recorded run only if everything that decided its result is bound or checked. **Bound before the red is proven:** the feature files (spec lock), the steps and drivers and the adapter's plumbing (`support` paths and patterns: `pytest.ini`, `conftest.py`, the feature binding module) in the bind lock (`bdd lock --scope bind --bound`), and the run record's hash of all of them (`inputs`). **Not taken from the caller:** the interpreter comes from `python = ` in the person-managed config or an in-project `.venv`/`venv`, never from environment variables (a process can set them for one command), and the runner is started without the variables the adapter names (`scrub_env`, `PYTEST_*`), with its own settings file (`-c`) and a conftest cut-off (`--confcutdir`), so a file elsewhere in the project cannot steer it. **Recorded and compared:** each run names its interpreter (path and hash) and the gate refuses another; the tripwire watches an in-project environment (interpreter, `pyvenv.cfg`, `.pth`, `sitecustomize`, the pytest packages); agents cannot write the environment or install packages. **Kept:** the run that proved the red is stored as `red.json` from the very bytes that were checked, and later runs cannot replace it. **Not covered, stated plainly:** third-party packages other than the runner's own can be changed by anyone who can run code as the person, which no check in the same account can prevent; the pinned, hashed install is the answer there. **Third round:** the runner never receives `PYTHON*` (except `PYTHONUTF8`, `PYTHONIOENCODING`), `LD_*`, `DYLD_*`, `BASH_ENV`, `ENV` or `NODE_OPTIONS`, and the adapter starts Python with `-X utf8 -I` (isolated, so neither the working directory nor the user site is imported from; a project that needs `PYTHONPATH` sets `pythonpath` in its bound `tests/pytest.ini`); one matcher (`*` within a path segment, no `**`) serves the guard, the lock and the digest, and a file that matches a bound path but was never locked is a violation; the tripwire also watches `entry_points.txt` of installed packages and the runner's dependencies. Production code runs inside the test process and could in principle detect and game the run: this is mitigated by the auditor reading the diff and by the optional mutation check, not prevented |
| D24 | Architecture view before coding | **Decided:** the system-map phase gets a small, reviewable design view, written as **Mermaid** in fenced blocks in a `design.md` next to `system.md` (flowchart for components and data flow, `sequenceDiagram` for the key interaction, `classDiagram` or `erDiagram` for the domain or data model, only the views the feature needs). The system-analyst writes it from the approved scenarios and the code it read; the step-engineer and the implementer read it before they bind and code; under `guided` the person sees it before binding, and at every level it is part of the report. Mermaid because it is plain text (a diff a person can review and a hash the tripwire can watch), needs no runtime, installer or network, and renders in GitHub, GitLab and VS Code. A stdlib-only check in the CLI (header present, balanced brackets, no `click`, `href`, `%%{init` or link directives, and every interface the diagram names also present in `system.md`) keeps it honest (`bdd design`; the gate runs it when `design.md` exists, and the playbook and the auditor's S7 ask for the file). **Reviewed and not imported:** `Agents365-ai/drawio-skill` (MIT; 45 scripts, draw.io XML, optional installers and network fetches, and a frontmatter that pre-authorises Bash and WebFetch) and `BESSER-PEARL/uml-drawing-skill` (Apache-2.0; class diagrams only, a Python DSL, and a rendering step that uploads the model files with curl to a third-party service). Both conflict with the rules that nothing is pre-authorised and nothing leaves the machine silently, and neither offers anything a stdlib CLI could reuse. Ideas taken in our own words: one textual source of truth, validate before rendering, state the file that was written. A person who wants editable draw.io files can install those skills themselves; they stay outside the plugin |
| D26 | Generic JUnit adapter | **Decided:** support any test runner through one adapter whose contract is the JUnit report, not a runner list. The project supplies the run command (`[adapters.run]` in the person-managed `.bdd/config.toml`, split into words and never run through a shell) and the step code; the adapter fixes what greenlight needs from it: one command runs one feature (`{tag}`, `{marker}`), one JUnit file at `{out}`, a test name that contains its scenario name (compared after dropping case and every character that is not a letter or digit, longest scenario wins, which is the mapping `bdd classify` already used), `BDD_EXPECTED_MISSING` in the failure text of a seam that does not exist yet, and loud build errors. Classification defaults cover common phrases of several languages (defects first, anything unknown blocks) and are meant to be extended after one run with a broken step and one with a failing assertion. Runners that write several files or to a fixed place go through `tests/run_junit.py`, a bound standard-library wrapper that deletes old reports, runs the command without a shell, merges every `testcase` into one file and keeps the command's exit status; it refuses a DOCTYPE or ENTITY like `bdd` does and patterns outside the project. A sample runner (`tests/run_tests.py`, unittest) ships so a fresh project is green before any runner is chosen and `bdd init --smoke` works. Runner knowledge lives in cards (`cards/runners/`), not in code, so a new runner is a Markdown file. **Not done, stated plainly:** the cards were written from each tool's documentation and are not exercised against the real tools in CI (only the wrapper, the sample runner and the classification are); a project should run its runner once and read the XML. Build failures that cannot be tied to a scenario leave the scenarios `not-run`, which blocks the gates but does not name the defect |
| D27 | Adopting existing code | **Decided:** an existing code base is brought under greenlight one bounded area at a time, as a feature of kind `adopt` (`bdd state init --adopt`, skill `/greenlight:adopt`, playbook `phases/adopt.md`). It reuses the normal phases, agents, human gates, locks and audit; what turns around is the evidence. Every scenario is tagged `@existing` and passes from the start, the bind gate pins the production source (`--record-red`), `tasks` and `implement` have no agent, and the implement and verify gates of an adoption feature refuse while a scenario is not `@existing` or the production source differs from the pinned one (`bdd adopt FEAT-n --check`, findings A1 to A3). Rules state observed behaviour and cite where it was seen; code that looks wrong is a question for the person, never a rule and never a fix. **Why not a separate pipeline or a new agent:** the existing gates already prove what matters (approved text, bound tests, a run that passes, an independent audit), and a second flow would need its own guard and tripwire. **Why not generate scenarios from a coverage run:** a characterisation test that nobody read proves nothing about intent, so a person approves the rules and the examples as always. **Not covered, stated plainly:** an adoption does not prove the existing behaviour is right, only that it is now described, locked and traceable |
| D28 | greenlight in tools without hooks | **Decided:** `bdd install-skills codex\|agents-md` writes plain-text instructions for other agent tools: Codex skills (`greenlight-<name>/SKILL.md` with only `name` and `description`, paths pointing at this installation, `/greenlight:x` turned into `$greenlight-x`) under `.agents/skills` or `~/.agents/skills`, or a marked block in `AGENTS.md`. These tools run no greenlight hooks, so the project is in **soft** enforcement and every artefact says so: the block and each skill open with it, `bdd doctor` warns (`enforcement`) when no hook has ever run or the mode is soft, the feature's state and the report already classify it as soft, and `--self-reported` approvals print that they are not verified by a hook. Soft approvals stay possible only when the person set `enforcement = "soft"` (or no hook ever ran), and CI is the recommended backstop: `bdd lock FEAT-n --check --require`, `bdd run`, `bdd classify --expect green`. Nothing is overwritten without `--force` (a differing file is reported and nothing at all is written until every target is clear), `AGENTS.md` is only changed between its own markers, links that leave the project or home folder are refused, and the destination is never taken from an argument. Not done: a prevention layer for these tools (hooks in Codex are user-configured, not shipped by a plugin) |
| D29 | Optional mutation check | **Decided:** an adapter or project opts in with an `[adapters.mutation]` table (`command` words without a shell, `{files}` as a word of its own, `{out}`, `threshold` as a kill percentage, `timeout`, `extensions`). `bdd mutate FEAT-n` runs it on the production files added or modified since the commit at which the red was proven, and records `.bdd/.runs/FEAT-n/mutation.json` (counts, score, files, hashes of the production source and of the tests; only this command writes it, the guard treats `.runs` as managed). The tool must produce a small JSON report (`killed`, `survived`, optionally `timeout`, `suspicious`, `skipped`), the one format a stdlib CLI can read for every stack. The report is written to a fresh private folder outside the project, so nothing in the project can have written it first; the tool must exit 0 (a non-zero exit fails the check; a wrapper turns survivors into counts), and the record keeps the command, the exit status and the report's hash. The check fails rather than passes when it measured nothing although something changed: production files changed but none matches `extensions`, no mutants, a non-zero exit. Only a feature that changed no production file passes as "nothing to mutate". When the table exists the verify gate requires a current result (same source and tests) at or above the threshold; without it behaviour is unchanged. No tool is a dependency of greenlight; the Python adapter only documents mutmut-style tools as an opt-in with a stdlib wrapper. **Why:** production code runs inside the test process and could, in principle, detect and game the run (see D23); the recorded runs cannot rule that out, a mutation check makes code that merely satisfies the tests visible, as survivors. It mitigates the limit, it does not remove it: an equivalent-mutant-heavy code base or a threshold set too low weakens it |
